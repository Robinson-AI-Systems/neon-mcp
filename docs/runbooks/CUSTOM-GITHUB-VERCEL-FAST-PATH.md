# Custom GitHub + Vercel MCP implementation fast path (owner-approved workflow maintenance, 2026-11-02)

**Use this for every subsequent Neon implementation session.** Entry: `AGENTS.md` → `SESSION-START.md` §0–1a → `STATUS.md` / ordered roadmap / actual open PR → chosen original card + full acceptance. This runbook chooses **how** to execute; it neither supersedes those rules nor adds a countable subsection. Custom GitHub **native Git + Robinson Playground is the preferred development environment**, including mobile sessions. Vercel Unleashed is the read-only deployment truth/diagnostics lane. The service's own Neon MCP is the only admissible source for independent provider/client acceptance.

## Primary workflow — persistent native Git workspace plus attached runtime

1. **Recover before starting:** use `github_batch` for up to ten *small* reads of main/live refs, open PRs, current card/status, current branch/CI/review. Large batch results may be omitted; retry those as individual `github_content_get` with bounded line ranges/byte continuation. On a red open PR, repair that head first. Use `github_workflow_pr_status` to see the next verified action. Use Vercel reads to reconcile READY and alias state, never infer served SHA from a branch name.
2. **Freeze original acceptance:** select 2–3 related *whole approved subsections* (repository sizing guide typically 2–5), capture their complete source requirements and negative/DB/door/provider criteria in the existing execution plan card, run `npm run session:bundle -- --card ...` when an engineering bundle is selected, and **commit the plan before implementation**. This runbook is not permission to skip `SESSION-START`'s released-work acceptance queue.
3. **Open native Git:** call `github_git_workspace_open` on `Robinson-AI-Systems/neon-mcp`, from verified `main` or an authorized existing unmerged predecessor, with a unique `requestKey`, a small idle lease and `runtime:"auto"` or `medium` where disposable PostgreSQL is needed. Use `github_git_workspace_read(status/refs/capabilities)` to prove branch and head. To create/switch a working branch use typed `github_git_workspace_run(operation:"switch",options:{branch:"ai/<tool>/<topic>",create:true,from:"main"},expectedGeneration:<latest>)` **only if the native capability report confirms those arguments**. Refresh generation after every mutation. Never commit on main.
4. **Attach runtime:** `github_playground_read(operation:"allocation")` until allocation, repo attachment and execution are truly ready; on any definitive failure choose the fallback below. Run `github_playground_execute` with `workspace_id`, `argv` and stable retry key. First `npm run session:prepare` (no tests/install), then narrow `grep -n ... path | head -50`, relevant source and focused test inspection. Use ordinary shell/git inside the **attached, isolated** runtime for scoped edits and tests; verify `github_git_workspace_read(diff/status)` at each coherent milestone. Do not put secrets into argv, shell output or Git.
5. **Build the full same-domain outcome:** include migrations (additive/rollback tested), Neon client route, policy/permission/confirm guards, public/internal doors/registry, safe errors, fake-provider request fixtures, **real disposable local Postgres** concurrency/denial tests and all caller/catalog/schema/README consequences. Preserve independent account/customer grants and protect actual production targets. Follow the card's exact acceptance. Use realistic fake fixture IDs only. Avoid restart-from-zero rewrites of merged features.
6. **Test economically:** run the relevant `npx vitest run ...`, targeted `npm run test:db -- tests/db/...test.js` when DB available, and `npm run check`; obtain command `exit_code=0`, not an accepted-execution acknowledgement. One test job at a time against a **shared local Postgres**, with reset before full DB run; GitHub Actions jobs remain isolated and parallel as configured. Never run `vercel dev`, watch, interactive prompts, or unbounded polling. Cap output, use `set -o pipefail`. On the final coherent tree run `npm run session:prepare -- --publish`, then all required full checks/suites once. Never weaken/quarantine tests. If local/Playground DB is unavailable, record exactly what could not run and require the real disposable-Postgres CI job.
7. **Publish safely:** inspect complete diff and matching plan. Make meaningful local commits using real Git (or the typed native `add` → `commit` operations) and **one normal git push/CI cycle** via the native workspace after verifying the branch has actual ancestry from current main. Do not use a snapshot/content commit for an already-pushed branch without reconciling remote HEAD. Never force push, bypass hooks or override protection. Verify remote commit tree and *every* intended file arrived; if not, fix before opening the PR. Use `github_workflow_open_pr` with card acceptance, concrete command evidence, test failures count, source diff, owner restrictions and **Self-review: findings/dispositions**.
8. **Repair/merge:** check `github_workflow_pr_status` for exact-head checks and reviews. Collect **all** failing jobs/logs once, reproduce locally, fix all root causes in one push, avoid overlapping CI runs. Inspect the whole diff against `AI-PR-READ-FIRST`. Check required exact-head `ci` and `release-policy` plus repository's underlying jobs, resolve legitimate reviewer findings; merge only via `github_workflow_merge_when_green` with `expectedHeadSha` and no overrides, when project rules permit. Confirm merged state and post-merge main checks. Release/production deployment is a separate existing scheduled/owner-approved path.
9. **Permanent handoff:** update the original card, `work-index.json`, `STATUS.md`, PLAN/design/ARCHITECTURE/GO-LIVE/OWNER-GUIDE where actual behavior changed, and acceptance queue; run all consistency checks. Report code, CI, deployed state, *independent* desktop/mobile/tenant/Neon-provider/RTC evidence and anything still open. Close idle workspace via `github_git_workspace_close` **only after verifying remote commit and PR**; closing deletes uncommitted data.

### One-off Playground for verification

If code is already on an immutable Git SHA and no interactive edits are needed, `github_playground_run({repo,ref:<full-sha>,argv:[...],requestKey:<new-key>})` provisions a fresh runtime, runs one bounded command and cleans up. Reuse the **same arguments + key only to resume** a not-yet-finished run; do not accidentally run the command twice. If command log is truncated, use `github_playground_read(logs)` with the execution ID and hash-pinned continuation. Do not claim disposable-Postgres proof from a lint-only run.

### Honest degradation when Playground or native Git is unavailable

- **First check current allocation and Git workspace state.** A runtime allocation may exist while `repository_attached:false` or `execution_available:false`; that is **not** an operational shell. Do not repeatedly request more capacity or promise it will attach. Use `github_playground_run` as an independently tested one-off alternative if supported.
- If native workspace is unavailable but GitHub API is reachable, use **`github_content_commit_git_data`** for an expected-head, ancestry-correct, count-checked atomic commit (up to 50 files per call) and `github_content_edit_files` for safe bounded patches. Review resulting remote tree. If a call throws/partially applies, **read the remote head, manifest and exact file bytes before retrying**; never replay a guessed write. When 50+ paths need changing, use native workspace/upload; split API commits only on verified heads and explain the split.
- CI runs source tests and disposable DB tests; do **not** describe this as a local pass. Use `github_workflow_pr_status` and targeted Actions job read/annotations to verify. Never manufacture a green from missing metadata.
- When a result is truncated, use the provider's original authenticated `github_get_result` / `vercel_get_result` handle (and exact provided paging); never infer missing bytes from a summary. Tool names/args can change; rediscover, don't guess.
- Cleanup is only for this task's owned workspace and verified closed-PR branches. Never delete other agents' work, production refs or unfinished open work.

## Vercel read-only deployment lane and release guard

At the start and after meaningful merges/releases:

1. Verify the authenticated Vercel team with `vercel_whoami`; list/find the **exact Neon project** and read `vercel_project_get`. The observed project uses production branch **`live`**, not `main`. Compare GitHub `main` and `live` explicitly.
2. Prefer `vercel_workflow_project_health` and `vercel_workflow_release_status` for consolidated status **if they actually succeed**. Fall back to `vercel_deploy_list(project,target:"production")`, `vercel_deploy_get` (READY/ERROR, branch, aliases, returned commit), `vercel_alias_list`, `vercel_env_list` (key names/target only) and specific build diagnostics. A `null` commit in Vercel results is unknown, not the `live` SHA. Corroborate serving code by a real version/health/manifest and immutable Git commit where the service supports it.
3. For preview diagnose the preview deployment of **the exact PR SHA**. Preview **shares the Neon MCP backing database**, so no production-capable profile or side-effect fixtures; do not use Vercel previews to test unsafe writes. Source-build, deployed-metadata, direct MCP client and real Neon provider checks remain separately labelled.
4. **Do not invoke** `vercel_workflow_deploy_and_wait`, `vercel_workflow_ship_to_production`, `vercel_workflow_emergency_rollback`, domain/project/env writes, any secret operation or production branch promotion without the repo's existing explicit authorization and checked release process. A Vercel MCP's ability to mutate is **not** permission. No money spending or live account changes.
5. When a high-level tool errors, capture its operation/error class and switch to the low-level read. On an inconsistent deployment/provenance report, mark exact evidence as unavailable and keep the relevant acceptance open. Do not call the custom Vercel connector a substitute for the custom **Neon** server's live API/RTC/provider acceptance.

## Micro-checklist for future agents

**Before code:** rules → existing red PR and release queue → current main/live/READY truth → frozen whole-card acceptance → native Git workspace + runtime ready.  
**During code:** reuse + one coherent outcome → fake-provider + real DB + denial/double-submit tests → focused checks → full checks once → true exit status.  
**Publish:** remote ancestry/tree/head → one PR/one CI cycle → all failure/review fixes → exact-head `ci` + `release-policy` → checked merge.  
**After:** deployed SHA independently corroborated or unknown → direct clients/Neon/provider/RTC acceptance kept separate → permanent original-card/status evidence, no fabricated completion.
