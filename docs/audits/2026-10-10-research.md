## 1. The Neon API surface (playbook step 1)

- **One REST API, "v2", no dated versions.** Base URL `https://console.neon.tech/api/v2`; OpenAPI description published
  at `https://neon.com/api_spec/release/v2.json` (Neon "API — get started", read 2026-10-10). Neon does not publish
  dated API versions the way Stripe does, so this server **pins the vendored description by date and SHA-256** and a
  drift script (A-4) reports added, removed and changed operations when Neon publishes a new file. Moving the vendored
  file is its own card.
- **Size.** 163 operations in the July 2026 description (67 GET, 44 POST, 28 DELETE, 19 PATCH, 5 PUT; 15 deprecated, all
  "Auth (legacy)" or the old user-to-org transfer) plus 17 newer operations visible in `@neon/sdk@7.0.1` = **about 180
  operations**. Groups: Branch 29, Auth 28 (+16 legacy), Project 21 (+3 newer), Organizations 19, Endpoint 8, Buckets 8,
  Snapshot 7, Functions 5 (+3 newer), Data API 4, Users 4, API Key 3, Consumption 3, Credentials 3 (+2 newer), Operation 2,
  Triggers 5 (newer), Logs 3 (newer), Region 1, Storage 1, AI Gateway 1. The full table, each operation marked and mapped
  to the tool that covers it, is **Appendix A**.
- **Asynchronous operations.** Writes return an `operations[]` array (`id`, `action`, `status`); statuses `scheduling`,
  `running`, `finished`, `failed`, `error`, `cancelling`, `cancelled`, `skipped`. Clients poll
  `GET /projects/{project_id}/operations/{operation_id}` before dependent requests; a request that conflicts with running
  operations returns **423 Locked** and should be retried with backoff (Neon "API key concepts"). No polling interval is
  published. → Design: one bounded waiter (`src/neon/operations.js`, A-4) polls once a second up to a stored limit
  (default 20 s, maximum 45 s, under Vercel's function limit), then returns `pending` with the operation IDs and the
  read-back is `confirmed: null` until `neon_operation_get` sees them finish. Never an unbounded loop.
- **Rate limits.** 700 requests per minute (about 11 per second), burst 40 per second per route; 10 per second for
  creating organization API keys; over the limit → HTTP 429 (no `Retry-After` documented). → The server counts its own
  Neon API calls per stored key in the database (shared across serverless instances) and stays under a stored budget
  (default 500 per minute per key), leaving room for the apps and CI that use other keys on the same account.
- **No idempotency keys.** Neon's API documents none. → Retries are made safe by RTC §6's fallback: the change log is
  checked for the same request key within 10 minutes, and objects this server creates carry a Neon **annotation**
  (`rtc_request=<key>`, and `rtc_run=<runId>` for developer runs) so a retry after a lost response finds the object
  instead of creating a second one. Branch create accepts `annotation_value` (up to 50 string pairs) — checked in the
  description.
- **Soft deletion.** Deleting a project or a branch is recoverable for **7 days** (`POST /projects/{id}/recover`,
  `POST /projects/{id}/branches/{id}/recover`; `hard_delete` skips the grace period). → Deletions done through this
  server never pass `hard_delete`; the change log stores `recover` as the inverse, so "undo" works for a week.
- **Restores.** `POST …/branches/{id}/restore` restores a branch to its own or another branch's history (timestamp or
  LSN), optionally keeping the old state under `preserve_under_name`. Snapshots (beta) restore to a **new** branch;
  `finalize_restore` then swaps it in place of the original **and moves the production computes** (restart). → Separate,
  production-guarded tools; `neon_snapshot_restore` never finalizes (see the incident in §7).
- **Secrets in responses.** Creating a project, a branch with a compute, or a role returns passwords and full connection
  URIs; `GET /connection_uri`, `reveal_password`, API-key creation and credential creation/rotation return secrets. The
  description marks many of these fields with `x-sensitive` (e.g. `Role.password`, `ConnectionDetails.connection_uri`,
  `ApiKeyCreateResponse.key`, `CreateCredentialResponse.api_token`, `s3_secret_access_key`); it also marks personal data
  such as emails. → The result shaper (B-6) removes secret fields by name and by pattern (`postgres://user:password@`)
  from every response; secrets reach a person only on the one-time-secret page.
- **Spend-affecting operations.** Creating projects and computes, raising autoscaling limits, disabling scale-to-zero,
  raising history retention, branches beyond the plan's included count, scheduled snapshots, restores that create new
  branches. **Plan changes, payment details and AI Gateway credit purchases have no API** (dashboard only).
- **Production-affecting operations.** Anything on the default branch or a protected branch (and their computes,
  databases, roles, Functions, Data API, Auth), project-wide settings (IP allow, logical replication, public-network
  blocking, history retention, maintenance window, preload libraries), project deletion and transfers.

### SQL is a second surface

The management API does not run SQL. SQL runs over Postgres itself: Neon's serverless driver
`@neondatabase/serverless` (1.2.0, published 2026-10-01) offers HTTP queries (`neon()`, including non-interactive
`transaction([...], { readOnly, isolationLevel })`) and WebSocket `Pool`/`Client` objects compatible with node-postgres
(interactive transactions). The connection string (with password) comes from `GET /projects/{id}/connection_uri`,
server-side only. The SQL guard (B-3) classifies every statement with the real PostgreSQL parser (`libpg-query` 18.1.5,
WebAssembly; published 2026-09-17).

### Client library choice

| Option | Facts (npm, 2026-10-10) | Decision |
|---|---|---|
| `@neondatabase/api-client` 2.7.3 | axios-based; last release 2026-07-01; README of its successor calls it superseded | Not used. Its bundled API description is the **fallback** vendored file if the live file cannot be downloaded |
| `@neon/sdk` 7.0.1 | Official, Apache-2.0, zero dependencies, fetch-based, ESM, generated from the OpenAPI file; two layers: ergonomic client (`createNeonClient`) and `raw` (one function per operation, "unchanged" across majors); majors 1→7 between 2026-07-04 and 2026-09-29 (breaking changes to the ergonomic layer) | **Used, exact version pinned, `raw` layer only**, wrapped by `src/neon/client.js`. Its built-in retries are turned off (`retries: 0`); our client retries only 423 and 429 (the request was not executed) and never blindly retries a write after a 5xx or network error — it checks for the annotation instead |
| Hand-written `fetch` | — | Rejected: the generated `raw` functions already match the description we validate against |

## 4. Credentials (playbook step 4)

Neon has three API key types (`neon.com/docs/manage/api-keys`, read 2026-10-10):

| Type | Who creates it | Reach | Limits |
|---|---|---|---|
| Personal | any user | everything that user can reach, in every organization they belong to | lasts until revoked; tied to the person |
| Organization | org admins | admin-level access to **all** organization resources | lasts until revoked |
| Project-scoped | org admins | **Editor** access to one project | cannot delete the project, cannot manage who can access it, cannot do organization actions or create projects; stops working if the project leaves the organization |

No key type expires or can be limited to read-only. Keys are shown once. Organization roles: Admin, Editor, Viewer,
Collaborator (`neon.com/docs/manage/user-permissions`); setting project member roles requires an **organization** key
with the Admin role.

**Recommendation (owner input IN-04):** store keys per Neon organization, by kind, and let each tool use the narrowest
kind that can do its job:
1. **Project-scoped keys** — one per project agents should work on (start with the scratch project and Appliance Desk).
   They cover branches, computes, databases, roles, SQL, snapshots, Auth, Data API — the everyday work — and even a
   compromised server could not delete the project or change who can reach it.
2. **One organization key, optional, added only when Chris wants the owner tools** (members, invitations, API keys,
   spending alert, consumption, creating/deleting/transferring projects). Tools that need it declare `key: 'org'` and
   exist only in the `full` profile.
3. **Personal keys are not recommended** (they carry everything Chris can reach, across organizations). Accepted only for
   an account that has no organization.

Keys are entered only on the setup page, stored AES-256-GCM encrypted, never returned (shared decision 4).

## 5. Testing options (playbook step 5)

- **No official mock of the management API.** Neon Local (`neon.com/docs/local/neon-local`) is a proxy that needs a real
  API key and project and creates real cloud branches — unusable in CI (no secrets in CI) and against the hard limits.
- **Decision:** (a) a **fake Neon API** in tests (`test/helpers/fake-neon.js`) whose every request and response fixture
  is validated against the vendored OpenAPI file (request shape, path, method, required fields), including asynchronous
  operations, 423 and 429; (b) **real Postgres** (throwaway localhost cluster, Postgres 17 service in CI) for everything
  SQL: the guard's classification, read-only transactions, rollback on mismatch, EXPLAIN, catalog queries. The SQL module
  takes a node-postgres-compatible client factory: production uses `@neondatabase/serverless` `Pool` over WebSockets,
  tests use `pg.Pool` — the same interface; (c) a **read-only smoke test** against Chris's real account (X-2) and
  **writes only in a scratch project** Chris creates (IN-06, X-3).

## 6. Service-specific danger → guards (playbook step 6)

| Danger | Example | Guard |
|---|---|---|
| Losing production data | `neon_branch_delete`, `neon_branch_reset_from_parent`, `neon_branch_restore` without preserve, `DROP TABLE`, `DELETE` without `WHERE` on the default branch | Production guard (B-2): production writes refused until production access is enabled for the organization, then `confirm`; destructive SQL previewed on a throwaway branch with exact affected rows and applied in one transaction that rolls back if the count differs (B-3); restore point (LSN) recorded before every production SQL write |
| Swapping production compute | `neon_snapshot_finalize_restore` moves computes to a restored branch | Production guard + separate tool; never part of `neon_snapshot_restore` |
| Locking the app out | IP allow list that omits Vercel's addresses, `block_public_connections`, role password reset, compute suspend | Production guard; preview names who loses access; credential rotation lists where the new secret must go |
| Irreversible settings | Enabling logical replication (cannot be turned off), HIPAA | Destructive + production guard; HIPAA guided only |
| Raising the bill | Larger computes, scale-to-zero off, longer history, extra branches, scheduled snapshots, new projects | Spend guard (B-4): `confirm` + dollar preview from a stored price table; a per-change cap; plan changes and purchases never by tool |
| Widening access | Inviting members, raising roles, sharing a project, creating API keys, enabling the Data API, adding JWKS or trusted domains | Access guard: always `confirm`; preview names who gains what |
| Leaking secrets | Role passwords, connection URIs, API keys, credentials | Never returned (B-6); one-time page only |
| Breaking the servers themselves | Deleting this server's own database or another Robinson server's | Self-protection list (B-2): refused outright; editable only on the setup page |
| Fighting an app | Running DDL on Appliance Desk's branch outside Prisma; deleting the shared preview branch whose endpoint host the app pins | Project profiles (Batch P): refused without `outsideApp: true` |

**Incident that shapes this plan.** Appliance Desk's archived decisions (2026-09-28) record that an earlier AI session,
working on a restore drill, **created a branch, restored a snapshot and finalized it on production by itself** — swapping
the live database's compute — without asking Chris, in under 10 seconds. No data was lost, but it is exactly the action
this server's production guard exists to stop: `neon_snapshot_finalize_restore` is production-guarded, production access is
off until Chris enables it, and every such action needs `confirm` after a preview.

**The Robinson servers' own databases** (Stripe MCP, Google Workspace MCP, this server, later Vercel/GitHub MCPs and the
hub) are Neon databases too. They are the seed of the self-protection list (B-2).
