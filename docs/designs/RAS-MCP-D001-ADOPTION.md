## 1. Baseline and scope honesty

Inspected Neon `main` `f4e2f5b6de11ccfca1d8a8b08fcd801ed7ea333c`. Native `/api/mcp`, S256 PKCE OAuth, client revocation and protected tool dispatch exist in source. `api/contract.js` currently returns 503 unless `RTC1_ENABLED=1`; `src/core/rtc-contract.js` emits an RTC **1** manifest and does not emit the RTC 2 dialect. `api/index.js` returns JSON information, not the required branded HTML front door; a fleet `/connection` page and Stage 1 public health response are not evidenced. The legacy direct-connection guide uses the older name/origin language. Do not infer live configuration, customer-client behavior, RTC 2 certification or deployed availability from these source observations. `docs/ARCHITECTURE.md` remains the as-built record and must be updated **only when implementation lands**.

Design overlays, **not new countable cards**: A-3 (OAuth/client identity), A-5/A-7 (protected setup, docs/front door), B-1..B-8 (guards, spend, audit, errors), C-1/C-2 (budgeted result/listing), R-1/R-2/R-3 (passes, HTTPS/manifest, conformance), O-4 (account/posture), X-2/X-3 (deployed/provider proof), CAP-1..CAP-5 (legitimate delegated authority) and CG-1..CG-6 (mandatory cross-cutting acceptance). Keep current work-index identities and original full acceptance; do not claim a small subtask completes a whole subsection.

## 2. Fleet identity, branding, and direct client surfaces

**Brand:** public first reference `Neon Unleashed by Robinson AI Systems`, short form `Neon Unleashed`; technical server `neon-mcp` and protocol names `neon_*` are **stable** and must not be renamed. Library D-005 **already claims** `neon-unleashed` and Coral `#FF5F5F`; do not make a duplicate claim. Use the fleet's approved Break-Out ring master and a single flat Coral shard; emerald `#00B67A`→teal `#00E3C2` ring, dark graphite/charcoal/mist fleet tokens. No provider logos, marks, fonts or confusing resemblance; no claim of Neon affiliation. Use the existing canonical SVG master and [Unleashed brand spec](https://github.com/Robinson-AI-Systems/library/blob/main/designs/ras-mcp-standard.md#unleashed--the-fleet-brand-system-standing-rule--chris-2026-11-02) rather than inventing a derivative.

**Target canonical origin (not yet verified attached):** `https://neon.robinsonaisystems.com`. On first launch / any separately approved identity migration, derive issuer, all OAuth issuer/authorize/token/register/revoke endpoints, protected resource `https://neon.robinsonaisystems.com/api/mcp`, client identity documents, manifest and public instructions from exactly **one** `PUBLIC_BASE_URL` configuration. Host/request headers and deployment aliases never set identity. Assert metadata/refusal/redirect consistency on both canonical and alias hosts. Historical `*.vercel.app` service addresses may continue responding as aliases and existing keyed connections are not broken; never register new OAuth connections against the platform hostname. If existing resource-bound grants need a one-time reconnection, disclose and sequence it with the owner's explicit identity-move timing rather than silently revoking credentials, rotating keys or reissuing grants. Do not attach DNS, change issuer or deploy from a design PR.

**Service-owned pages:** `GET /` displays a branded, accessible HTML status front door with actual status, version, deployed SHA, tool count, safe posture, endpoint and discovery links **derived from the same live state as health**, not hardcoded. `GET /connection` is "My connection": instructions for ChatGPT, Claude, Muse, Hermes, coding clients, direct MCP, bearer/API-key passes and optional Hub; sign-in claims an existing principal; shows selected rights and registration posture, no secret inputs in chat, and precise disconnect/revoke. Fleet website blueprint owns typography, dark UI, button/feature components, disclaimer block, privacy/terms links and copy. Server content must not imply availability beyond evidence.

**Fleet website** (site repository owns publishing): exactly one truthful `/tools` record for `neon-unleashed`, with factual ability and non-affiliation, correct Coral mark, and "In development" until independently accepted. A Connect button is enabled **only after** the branded `/connection` responds live; public product detail / address requires the website's stronger proof gate. This Neon design does not authorize cross-repository edits or public launch.

**Client matrix and packaging:** verify ChatGPT phone/browser/desktop, Claude phone/browser/desktop, Muse, Hermes Agent, Claude Code, Cursor, Windsurf, VS Code, Codex and Gemini CLI. Record exact version/device/date, first-hand owner observation versus vendor documentation, supported/failed/untested; never silently mark unsupported clients passed. Every client shape gets a protected, ready-to-copy configuration guide in the server-shipped connector package (including Hermes `config.yaml` and a deliberate per-client tool allowlist). Remote Streamable HTTP is baseline; preserve direct MCP independent of Hub. A genuine initialize at client-supported protocol versions, authenticated `tools/list`, real authorized named tool call, and wrong-credential refusal are required before claiming support.

**Dual credential shapes:** accept client-supported bearer/API-key style via a scoped **pass on RTC HTTPS**, and supported connector-token OAuth on native MCP; do not quietly interchange credentials between those doors (RTC 2 §4.2). For native clients support both public PKCE S256 `none` and confidential clients via declared registration/CIMD as applicable, no mandatory client secret for mobile, and truthful `WWW-Authenticate`/issuer metadata. Pass creation, provider keys and other secrets use server-owned protected setup fields and one-time display only, never tool arguments, tool results, docs, chat or logs. **Resource parameter reconciliation:** RTC 2 Hub OAuth clients MUST send RFC 8707 `resource` at authorization AND token exchanges. The RAS Standard records genuine mobile clients that omit the parameter; preserve security by designing a separately tested native-client compatibility path only if the server has exactly one fixed canonical protected resource and binds the resulting token to that exact resource. Never mint unbound tokens, accept a conflicting requested resource, infer from Host, or weaken Hub RTC 2 conformance; if the standards and a particular client cannot be reconciled safely, record client as failing with a remedy rather than inventing success. Freeze this detail in A-3 with real client fixtures before implementing.

## 5. Ordered implementation and checks (not authorization to perform live acts)

1. **First, safe source/backward-compat inventory** — A-3/C-1/C-2/R-1/R-2 current route, manifest, auth, stored result dialect, pass tests, risk, default posture and existing client sessions. Freeze applicable current full card criteria and capture actual gaps. RTC 1 and current OAuth must continue working; never silently change old dialect or turn on `RTC1_ENABLED` from a design update.
2. **Authentication + protocol work, one cohesive guarded outcome** — A-3, R-1, R-2, C-1/C-2 as related pre-existing cards; new correct RTC 2 manifest only when all doors actually pass, resource-stable public/confidential flows, scoped pass and provider-owned risk layers, cursor and content-byte recovery, real PG concurrency tests. Keep direct MCP independent of Hub; use one coherent PR only when cards are fully implemented per repo rules.
3. **Front door + health + brand and explicit operating posture** — A-7/O-4 and relevant R-2 gates; preserve old URLs while owner later authorizes domain/issuer attachment, mirror website blueprint and already-claimed Coral mark. Do not publish speculative status or add broken buttons. Site `/tools` is an external follow-up owned by its project, not an action in Neon.
4. **Conformance + client proof** — R-3, X-2/X-3 and CG-1..CG-5: pre-deploy client handshake matrix, fixture-backed RTC 2 suite with probe→section map, two-store tests, independently verified actual direct Neon read, safely authorized scratch write/readback/cleanup and revocation. Keep every skip visible.
5. **Release and fleet readiness** — normal scheduled `live` promotion only; compare exact main vs checked READY live and source→manifest `revision`; run nine protection sections, privacy sweeps/Terms/Privacy, rollback and fixture expiry. Gate public listing/production-ready claims and commercial operations through their respective external approvals.

**Tests and acceptance records**: for each case record card, source SHA, tested deployed SHA, exact safe client/version, auth shape, principal scope (redacted), real operation name, expected allow/deny, result, cleanup, timestamp and status. Expected negative cases include wrong token type on wrong door, refresh downgrade/replay, foreign cursor/handle, revoked pass, expired pass, ambiguous/mismatched OAuth resource, wrong Host, old deployment alias/issuer drift, duplicate submit, outage health 503, expired fixture, cost uncertainty and missing legal disclaimer. Unit/integration/CI alone are not live client/provider evidence. Existing completion gates remain OPEN until separately verified.

## 6. Decision and release boundaries

This design records pre-existing owner rulings from D-001 and RTC 2; it does **not** adopt a new wire dialect by fiat, alter `work-index.json`, approve a domain switch, make the app public, spend money or change production. Runtime as-built truth belongs in `docs/ARCHITECTURE.md`. Any ambiguity requiring a new owner decision goes into `docs/DECISIONS.md` first. Where the Standard is a *living* policy and RTC 2 is a *versioned* wire spec, follow D-001's product/UX/safety doctrine while preserving RTC 2's exact declared wire shape and contract-version freeze. No Hub live connection is a Neon acceptance prerequisite.
