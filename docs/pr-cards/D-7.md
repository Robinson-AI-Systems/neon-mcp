## Verified API and seams
- `GET /projects/{project_id}/snapshots` → `listSnapshots`, `{snapshots:[Snapshot]}`; Snapshot has id/name/created_at and optional source_branch_id/manual/full_size/diff_size.
- `GET /projects/{project_id}/branches/{branch_id}/backup_schedule` → `getSnapshotSchedule`, `{schedule:[BackupScheduleItem]}`, with bounded frequency/retention/time fields.
- `getProject` independently confirms project ID and organization, `listProjectBranches` confirms all branch IDs for schedules; use only the project-scoped verified key, projectRead, defineReadTool, and existing dispatcher. Empty/over-limit/unverified source must not be disguised as complete. Source branch of a historical snapshot may no longer exist and should remain an ID, not falsely claimed currently active.

## #97 — destructive manual development snapshot deletion (offline)

`neon_snapshot_delete` is a separate owner-only B-1 destructive write. It verifies project/org, full bounded snapshot and branch inventories, the exact manually created snapshot, and a currently existing explicitly non-default/unprotected source branch via a second independent GET before preview. No scheduled, orphaned, protected or default-branch snapshot can be deleted. The apply path repeats the full inventory and strict snapshot identity check, refuses drift, sends only the pinned `deleteSnapshot` request and independently verifies its disappearance without replay. Provider uncertainty stays PENDING; all protections, protected app/production gates, durable audit and exact request-key semantics are inherited from `defineWrite`. This operation does not create storage or additional scheduled consumption; it permanently removes a recovery point and needs explicit confirmation. Fake-Neon write-contract and refusal tests, not live acceptance; no actual data was deleted.

## #98 — snapshot rename without retention expansion (offline)

`neon_snapshot_update` is registered as a B-1 owner-full metadata rename **only** for an existing manual snapshot of a verified non-default/unprotected development branch. Reuse D-7's exact project, snapshot, branch and current-protection verification. Refuse duplicate names, unchanged names, invalid text or missing inventory. Apply repeats all verified identities and snapshot metadata and issues a fixed pinned `updateSnapshot` PATCH containing **name only**, never `expires_at` or another field. Post-write readback checks that only the name changed. Every B-1 protected/app/production/audit and uncertainty guard still applies; no live resource or price-affecting retention change. The future expiration update must acquire independently reliable incremental storage cost evidence and B-4 approval.

## #99 — cost-admitted manual development snapshot creation (offline)

`neon_snapshot_create` uses full-owner B-1 and B-4, with current live organization plan verification (Launch/Scale), source-dated snapshot storage price `$0.09/GB-month` from the pinned 2026-10-10 Neon pricing table and conservative manual-full-snapshot forecast of **2x verified current branch `logical_size` plus 1 GB**, billed as a month even though owner must choose finite UTC expiry within seven days. Estimation is not a guarantee: a live writer could change logical size after the preflight. Both plan and amount need durable owner spend admission, per-change/daily caps, project/app/production/protected guards and explicit confirmation; no live mutation is authorized or tested. The branch must exist, be explicitly nondefault/unprotected in independent GET and complete listing, have known safe integer logical size under 100GB and a unique safe snapshot name with capacity under the 100-manual limit. Apply repeats project, protection, name, inventory, observed logical bytes and admission basis; it sends exact pinned `createSnapshot` query `name` and `expires_at`, never point-in-time LSN or historical inputs, and verifies a single new provider-ID manual snapshot with the expected source and expiry. Uncertain attempts are never replayed. Fake-provider tests cover provider request, source-dated amount, success, drift and guard refusal; real provider/billing remain OPEN.

**Contract mismatch kept isolated:** The publicly documented snapshot update API lists `expires_at`, but the unmodified July-2026 pinned vendor `SnapshotUpdateRequest` only accepts `name`. `neon_snapshot_update` remains name-only. No direct vendor-file edits, schema bypasses or claims of expiry-update acceptance; separately sourced repinning is needed before reconsidering retention changes.
