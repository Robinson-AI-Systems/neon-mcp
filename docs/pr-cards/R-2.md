## 2026-11-03 — persistent per-pass RTC request cap (source stage, unmerged)

The existing owner-only, project-key-scoped, 24-hour, read_only/preview
temporary RTC pass now accepts an **owner-selected** request limit from
**1 to 60 calls per minute** (default **60**, retaining old behavior).
The limit is integer-validated both in the owner setup form and the
issuer/storage boundary, stored per hashed pass, read back for admission
and enforced using the existing atomic PostgreSQL budget method. All
server instances use the same persisted counter and exact pass hash;
a rejected call receives an HTTP 429 with the remaining current-window
Retry-After seconds. A malformed stored limit fails closed before
consumption. The existing key-verification, revocation, expiry,
read_only/preview/allow_writes=false and server/discovery area restrictions
were not relaxed.

An additive nullable-free column
`oauth_tokens.rtc_requests_per_minute INTEGER NOT NULL DEFAULT 60`
keeps previously issued passes at their original cap. The owner form
shows the selected limit and the existing one-time protected pass
exchange still never emits token values into receipts or logs. The
safe RTC whoami result exposes the cap, not the secret. The concrete
unit and disposable-Postgres regressions include two adapters racing
eight same-pass calls under a cap of three: exactly three admitted,
five 429, revoked next request 401. Invalid rate/owner form and
malformed stored grants are refused before using the provider.

**Whole R-2 remains IN_PROGRESS, ZERO original-subsection credit.**
The new mechanism proves only this criterion's bounded rate-limit
portion, not general RTC 2 production availability. Native-client
conformance, all-pass scope/writes, independent provider evidence,
issuer separation and deployed SHA require independent completion.
No new live pass was created and no production database was changed.
The additive migration is inert in this unmerged branch.
