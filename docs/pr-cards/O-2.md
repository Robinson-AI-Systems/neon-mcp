2. `neon_apikey_create` audits/guards actual provider key creation and handles raw tokens exclusively via owner-passphrase-controlled one-time exchange OR secure server-encrypted enrollment without a tool result containing the token; generated key name is `robinson-neon-mcp-<purpose>-<date>`. Fail-closed partial completion; no automatic resend after uncertainty. Scoped project keys cannot be invented from unsupported APIs.
3. `neon_apikey_revoke` identifies an exact provider key by provider ID/kind/scope, refuses revoking any active server credential or the `robinson-neon-mcp-` family while it is still in use without verified replacement; always previews target and immediate integration effect, performs B-1 one-use confirmed action and independent revoked/absent readback. No self-lockout.
4. `neon_transfer_request_create` identifies and independently verifies selected project/default branch/current owner and any known integrations, requires canonical production+protected/app safeguards, previews irreversibility, and places claim link only in a one-time owner page, never tool result.
5. `neon_transfer_projects_between_orgs` verifies all source project/org identities and destination scope/authorization, previews every project and known Vercel/GitHub integration consequences, is owner-confirmed and production-guarded for every project, and validates post-transfer absence/source + destination ownership or explicitly pending evidence without replaying uncertain mutations.
6. Realistic fake Neon provider wire method/path/params, one-time secret privacy and consumption, revoked key self-protection, hostile input, cross-org, provider uncertainty/replay, protected or app-owned project, readbacks and normal shared door/profile tests.
