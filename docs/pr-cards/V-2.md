## Bounded public CSV/JSON ingestion into an isolated demo table (source pending CI)

- `neon_dev_seed` now accepts an exclusive `sourceUrl` to a public HTTPS
  `.csv` or `.json`, creates one isolated `rmcp_import_*` schema and
  `import_rows` table on the same previously enrolled, unprotected, expiring
  run-owned development branch as the synthetic scenario path.
- Strict server-side HTTPS: no custom ports, credentials, private/local host or
  IP literals, redirects or compressed bodies. Resolve and require a public
  IPv4 address, pin the socket to it while normal TLS verifies the original
  host, enforce timeout/header/content-size and fatal UTF-8 decoding.
- Validate CSV quoted fields or simple JSON object arrays, identical
  safe column headers (max 16), at most 900 data rows and 256 characters
  per cell, integer/boolean/date/text inference, fictional example.com
  emails/555-01xx phones, no password/secret/token/SSN/DOB/address keys.
  Constraints and duplicate safe IDs are validated before writes.
- Each file is fetched during preview and fetched a second time before
  apply; its exact SHA-256 digest and row/table counts must match.
  Adaptively pack trusted normalized cells into at most 18 parameterized
  JSONB INSERTs plus 2 DDL statements, ≤8,192 characters per parameter.
  Apply only through existing B-1/B-3 and verify every inserted cell on an
  independent SQL connection. The service never echoes or audits source rows,
  query strings, or arbitrary raw SQL. Errors and source races fail closed
  and never authorize a blind retry.
- Unit SSRF, transport, data-validation, B-3 plan, B-1 confirmation/replay
  and mismatch tests and real PostgreSQL 500-row/unique/readback tests are
  authored, not yet independently verified by this paragraph. The initial
  `auto` existing-schema mode remains unimplemented. Full public-file
  acceptance needs an owner-approved safe public fixture and checked release.

## Existing-schema auto mode — implementation checkpoint

The original **V-2** subsection includes `scenario: "auto"` with an explicit
`existingSchema`, 1–100 synthetic rows/table, and an active service-owned,
expiring, nondefault and nonprotected development run. No new subsection or
standalone roadmap unit is created. Only the existing full-owner `neon_dev_seed`
write-contract/guarded B-3 transaction is used. It performs fresh, bounded,
read-only PostgreSQL catalog inspection, checks identifiers, one-column
integer PKs, same-schema FKs, FK cycles, unique constraints and supported
numeric CHECK clauses; RLS, custom triggers, unidentified unique indexes,
cross-schema references, unknown column types and unsupported constraints
fail closed before write. Plans seed 1–6 eligible existing tables in parent
order using synthetic-only parameterized JSONB batches, skip conflicting
unique/CHECK rows and propagate skipped parent rows to dependents. It
recomputes a catalog/row fingerprint before apply and compares every
inserted cell independently afterward. Duplicate B-1 request keys never
resend SQL; unexpected SQL results remain pending rather than success.
