# O-1 — Organization membership, invitations and project access

Status: **IN_PROGRESS — planned, not accepted**. Original approved subsection **O-1** in `docs/designs/BATCH-O.md` §4, with no newly invented countable units. Base: `b6350728b25465c06acf562c92651fa82e27b0d4`. V-4's source was merged in #177; external/provider acceptance remains separate.

## Pre-code drift and authority
Reuse `projectClient`/encrypted key vault, `projectRead`/budgeted SDK and `defineWrite`'s audited preview/confirmation/replay behavior, read descriptors and the unified `src/tools/index.js` registry. Project-scoped keys MUST NOT elevate to organization scope. Re-fetch trusted organization/member/project access before mutations; write APIs require provider-confirmed method/path/body and independent readback. Organization invitations send real external email and are **not authorized for live execution by this developer session**. The product is designed for the legitimately entitled end user and delegated coding agent, rather than inheriting the implementation agent's spending/activation limits.

Provider contract reconciliation: Neon currently documents that organization invitation creation may require a **personal admin API key** rather than an organization key. Verify the pinned SDK/schema and keep unsupported credential paths explicit without pretending the current organization-key vault can perform them. Never guess the caller identity from the selected connection or member email when guarding self-lockout.

## Frozen original acceptance (one complete O-1)
1. `neon_org_list` and `neon_member_list` return organization/member/invitation scope without exposing secrets, using correct provider identity and pagination.
2. `neon_member_invite`, `neon_member_set_role`, `neon_member_remove`: clear target/emails/roles and impact in preview; explicit B-1 owner confirmation, audit and readback; last-admin and credential-owning member self-lockout refused; no replay after uncertainty.
3. `neon_access_list`, `neon_access_set_project_role`, `neon_access_share_project`, `neon_access_revoke_share`: exact independently verified organization/project and member/share identifiers; access widening disclosed and confirmed through all doors; readback and denial for missing/stale/foreign scope.
4. Project-only credentials refuse with an actionable organization-key explanation; provider-required personal credentials must be represented truthfully with a secure enrollment path, not an artificial permanent product denial.
5. Unit, provider-request-shape, fraud/cross-tenant, replay/uncertainty, integration, and write-contract tests; full exact-head check/unit/db/ci/release-policy and independent review before merge. Genuine deployed provider/user acceptance stays separately pending.
