## A-3a — primitives and database methods

- `src/core/oauth.js`, `src/core/http.js` copied as is (random tokens, SHA-256 hashing, PKCE S256, redirect validation,
  login lockout `MAX_FAILED_LOGINS = 5` in `LOCKOUT_WINDOW_MINUTES = 15`, client IP normalization).
- `src/db.js` gains: `createOAuthClient`, `getOAuthClient`, `createAuthCode`, `consumeAuthCode` (single use),
  `createAccessToken`, `getAccessToken`, `getTokenByRefreshToken`, `rotateRefreshToken` (one atomic `UPDATE … RETURNING`;
  copies every `CONNECTION_FIELDS` column from the issuing row; only for the same `client_id`), `revokeAccessToken`,
  `recordLoginAttempt`, `markLoginAttemptSucceeded`, `countRecentFailedLogins`, `listNeonOrgs` (id, label,
  `production_enabled`, `is_default`). Codes, client secrets, access and refresh tokens stored only as SHA-256 hashes.
- `test/helpers/fake-db.js`: the same methods in memory (mirror Stripe's fake at `e2f90e8`, renamed fields).
- Tests: `tests/unit/oauth-core.test.js` (hash, PKCE, redirect rules, lockout counting); `tests/db/oauth.test.js` (real
  Postgres: 5 wrong passphrases from one address in 15 minutes lock it; code single use; tokens stored hashed —
  `SELECT` finds no plaintext; refresh only for the same client; revoked and expired tokens refused; two concurrent
  rotations of one refresh token → exactly one succeeds; after a refresh the new token keeps `neon_org`,
  `project_scope`, `mode`, `profile`, `listing`); `tests/unit/connection-fields.test.js` fails if `oauth_tokens` gains a
  connection column (from `initSchema`'s SQL) that `CONNECTION_FIELDS` does not list.
