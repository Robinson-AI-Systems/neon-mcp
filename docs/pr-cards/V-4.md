## Full acceptance criteria and integration boundaries

1. `neon_dev_anonymized_copy`: require full owner profile, verified project,
   source branch and selected database, explicit B-1 confirmation, B-4
   source-dated branch+compute spending estimate/caps, checked V-1 active run
   ownership, TTL and compute settings. Read bounded metadata only; refuse
   undetected/unsupported column catalog, missing masking rule on **any**
   sensitive column (including `email`), inconsistent duplicate rules,
   unsupported masking expressions and ambiguous input. Call Neon's beta
   `createProjectBranchAnonymized` with complete initial rules and
   `start_anonymization:true`, expiring unprotected child, bounded compute,
   run annotation and independent provider identity/masking-status
   verification. Record exact created ID in run cleanup ledger. Raw/unmasked
   data must never be returned or advertised as safe. Pending/error/unknown
   provider results remain pending, no blind retries.
2. `neon_dev_tune_query`: require full owner and an active recorded
   nonproduction expiring target; accept one AST-checked SELECT and verified
   predicate, no untrusted SQL writes or unsupported expressions. Create a
   separately priced, bounded, expiring **disposable child**; run
   `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` only there before and after
   limited index experiments; return safe timings, scan evidence and at
   most three identifier-quoted, valid `CREATE INDEX CONCURRENTLY`
   recommendations for the existing index tool. Never create an index on the
   original branch; delete and verify child cleanup even on errors. Unknown
   result, orphan child or lost response stays pending.
3. `neon_dev_check_integration`: direct independent full-scope read-only
   integration checklist: expected tables, migration/version, extensions,
   roles, pooled host metadata supplied by caller (never a secret),
   default-branch protection, development expiry, Neon Auth/Data API
   availability and current branch/compute quota. Each check is explicitly
   `ok` or `missing` with an owner action/tool name; no mutations.
4. Unit/fake-provider, real disposable PostgreSQL, write-contract, SQL safety
   and denial tests cover all three workflows; production refused where it
   would be written (masked source is read-only exception), app-owned
   operations guarded, missing `email` rule refused, source untouched
   during tuning, CREATE INDEX valid and integration fixture all-ok/one
   missing per check. Verify exact-head check/unit/db/ci/release-policy,
   security self-review, review reconciliation and post-merge main.
5. Deployed custom MCP + actual provider scratch creation, anonymization,
   tuning and cleanup are separately gated owner/provider acceptance.
   No autonomous spending or production activation approved.
