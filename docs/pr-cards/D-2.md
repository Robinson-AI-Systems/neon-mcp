## PR #54 stall cause and repaired integration

The pinned @neon/sdk 7.0.1 raw layer omits recoverProjectBranch despite the vendored API spec documenting the route. The central Neon client owns the low-level fetch client as `client.sdk = createNeonClient(...).client`. The initial compatibility adapter incorrectly called `client.sdk.client.post`, making recovery fail while other tests remained green. Use central `client.recoverBranch`, which calls `sdk.post` with its captured setup-only API key as Bearer header; generated raw methods add auth themselves, but low-level post does not. Exact POST /projects/{project_id}/branches/{branch_id}/recover and path identifiers, preserving the single API budget, retry/idempotency policy and fake-Neon validation. Regression: `tests/unit/fake-neon-sdk.test.js` must prove operationId recoverProjectBranch and signed POST through the configured SDK. No direct HTTP or new secret route.

## PR #55 preserved restore and reset implementation (verified baseline #54)

New `src/tools/branch-restores.js` exports `neon_branch_reset_from_parent` and `neon_branch_restore`, both using B-1 `defineWrite`, `createProjectWriteContext` with independent branch classification, B-4 `createSpendGuard.price`, and `applyNeonWrite` with vendored `restoreProjectBranch` POST /projects/{project_id}/branches/{branch_id}/restore. After apply, GET verifies target identity, a distinct newly preserved branch and target last_reset_at or updated_at changed; ambiguity returns unconfirmed rather than success.
